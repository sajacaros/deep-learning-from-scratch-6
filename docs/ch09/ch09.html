9장. 학습 (도전편)

기울기 누적 → DDP·ZeRO → Muon → WebBot 150M 사전 학습 · 10개 절

한 줄 요약 — 모델이 커지면 GPU 메모리가 가장 큰 벽이 된다. 기울기 누적과 기울기 체크포인트로 GPU 한 장의 메모리를 아끼고, 데이터 병렬(DDP) 과 ZeRO로 여러 GPU를 쓰며, Muon 옵티마이저로 수렴 속도와 메모리 효율을 높인다. 이 기법들로 150M 파라미터의 WebBot을 10만 스텝 사전 학습해 검증 손실 약 3.0에 도달한다.

9.1 기울기 누적 (Gradient Accumulation)

배치가 클수록 각 층의 중간 출력(역전파에 다시 필요해서 저장해 두는 값)도 늘어 메모리를 많이 쓴다. 그렇다고 배치를 줄이면 학습이 불안정하거나 느려진다.

→ 작은 배치(마이크로배치)로 순전파·역전파를 여러 번 하면서 기울기를 쌓고, 갱신은 한 번에 한다.

accumulation_steps = 4                    # 마이크로배치 8 × 4 = 유효 배치 32
optimizer.zero_grad()
for i, (inputs, targets) in enumerate(dataloader):
    logits = model(inputs)
    loss = F.cross_entropy(logits, targets) / accumulation_steps   # ⭐ 손실 조정
    loss.backward()                                                # .grad에 더해짐
    if (i + 1) % accumulation_steps == 0:                          # 4번마다 갱신
        optimizer.step()
        optimizer.zero_grad()
  • 파이토치는 backward()를 부를 때마다 기울기를 .grad에 더한다. zero_grad() 전까지 계속 쌓인다.
  • cross_entropy는 기본이 평균(reduction='mean')이므로, 큰 배치 한 번과 같아지려면 accumulation_steps로 나눠야 한다.

왜 성립하나 — 전체 배치 (: 누적 횟수, : 마이크로배치 크기)

마이크로배치별 평균 손실을 으로 나눠 더하면, 전체 배치를 한 번에 처리한 평균 손실과 같다. 미분은 선형이므로 기울기도 같다.

⚠️ 정확히 같아지는 건 손실이 샘플별로 독립일 때다. 배치 정규화처럼 배치 통계를 쓰는 층이 있으면 결과가 조금 달라진다(WebBot은 RMSNorm이라 해당 없음).

9.2 기울기 체크포인트 (Gradient Checkpointing)

기울기 누적이 "배치를 쪼개서" 아낀다면, 기울기 체크포인트 [Chen et al., 2016]는 중간 출력을 덜 저장해서 아낀다. 일부만 저장하고 나머지는 역전파 때 다시 계산한다 → 메모리 ↓, 학습 시간 ↑.

from torch.utils.checkpoint import checkpoint

class GPT(nn.Module):
    # ...(생략)
    def forward(self, ids):
        x = self.embed(ids)
        for block in self.blocks:
            x = checkpoint(block, x, use_reentrant=False)   # 블록 내부 출력은 저장하지 않음
        x = self.norm(x)
        return self.unembed(x)
  • use_reentrant=False: 제약이 적고 불필요한 재계산도 줄여 현재 권장되는 설정. True는 예전 코드와의 호환용.

무엇을 저장하고, 무엇을 다시 계산하나

역전파는 각 층의 기울기를 구할 때 그 층의 입력과 중간 활성값을 다시 쓴다. 예를 들어 Linear의 가중치 기울기는 입력 가 있어야 계산되고, SwiGLU·softmax·RMSNorm도 순전파 때의 값을 쓴다. 그래서 보통은 순전파 동안 이 값들을 모두 저장해 둔다. 블록 하나 안에는 어텐션 점수, Q·K·V, FFN의 넓은 중간값(2,048차원) 등이 있어서 블록 입력(768차원) 하나보다 훨씬 크다.

순전파 때 저장하는 것 역전파 때 하는 일
체크포인트 없음 블록 안의 모든 중간 활성값 저장된 값으로 바로 기울기 계산
checkpoint(block, x) 블록 입력 하나만 그 블록의 순전파를 한 번 더 돌려 중간값을 되살린 뒤 기울기 계산

직접 확인 — webbot/model.py의 GPT(WebBot 설정, 12블록)에 B=1, C=256 입력을 CPU·FP32로 넣고, 블록들이 역전파용으로 저장한 텐서 크기를 torch.autograd.graph.saved_tensors_hooks로 세었다.

블록이 저장한 활성값 블록 순전파 횟수 (순전파 + 역전파)
체크포인트 없음 192.3MB 12 + 0
블록마다 체크포인트 9.4MB (= 블록 입력 0.79MB × 12) 12 + 12
  • 저장하는 활성값이 약 1/20로 줄었다. 대신 역전파 중에 블록마다 순전파가 한 번씩 더 돌았다.
  • 두 경우의 기울기는 모든 파라미터에서 완전히 같았다(최대 차이 0). 같은 계산을 다시 할 뿐이라 결과는 변하지 않는다.
  • 비용은 대략 순전파 한 번이다. 역전파는 순전파의 약 2배 계산이므로(8.1절 의 + ), 스텝 전체 계산은 약 4/3배가 된다.

💡 저장소의 webbot/model.py와 ch09/01_pretrain.py에는 체크포인트가 적용되어 있지 않다. 메모리가 부족할 때 위처럼 forward()만 바꿔 쓰면 된다.

9.3 분산 학습 — 데이터 병렬

방식 나누는 것 언제
데이터 병렬 학습 데이터(배치) 모델이 GPU 한 장에 들어갈 때 → 이 책의 범위
모델 병렬 모델 자체 모델이 GPU 한 장에 안 들어갈 때
  • All-Reduce: 모든 GPU의 기울기를 더한 뒤, 그 결과를 다시 모든 GPU에 나눠 주는 연산. 모두 같은 기울기로 갱신하므로 모델 사본이 항상 같은 상태로 유지된다.
    • 💡 파이토치 DDP는 더한 기울기를 GPU 수로 나눠 평균을 쓴다. 각 GPU의 손실은 자기 몫 배치의 평균이므로, GPU들의 기울기를 평균하면 전체 배치를 한 GPU에서 평균 낸 손실의 기울기와 같다. 9.1절에서 마이크로배치 손실을 으로 나눈 것과 같은 논리다. 합을 그대로 쓰면 기울기가 GPU 수만큼 커져서, GPU를 늘릴 때마다 학습률을 줄여야 한다.
    • 직접 확인: CPU에서 gloo 백엔드로 프로세스 2개를 띄워 Linear(3, 1)을 DDP로 감쌌다. 랭크 0·1의 기울기 첫 원소가 각각 0.3458, −0.3968일 때, DDP 후 두 랭크의 기울기는 모두 −0.0255였다. 합(−0.0509)이 아니라 평균이다.
  • 프로세스와 랭크: 보통 프로세스 1개가 GPU 1장을 맡고, 각 프로세스는 랭크(rank) 번호(0, 1, 2, 3)로 구분한다.

DDP (DistributedDataParallel)

import os, torch
import torch.distributed as dist
from torch.nn.parallel import DistributedDataParallel as DDP

dist.init_process_group(backend='nccl')         # 1. 프로세스 그룹 초기화 (NVIDIA GPU 간 통신)
local_rank = int(os.environ['LOCAL_RANK'])      # 2. 이 프로세스가 맡을 GPU 번호
torch.cuda.set_device(local_rank)
model = GPT(config).to(local_rank)              # 3. 해당 GPU에 모델 배치
model = DDP(model, device_ids=[local_rank])     # 4. 감싸면 backward 때 All-Reduce 자동 수행

$ torchrun --nproc_per_node=4 train.py          # GPU 4장 → 프로세스 4개

torchrun이 RANK, LOCAL_RANK 같은 환경 변수를 각 프로세스에 넣어 준다.

9.4 ZeRO (Zero Redundancy Optimizer)

데이터 병렬은 GPU를 늘려도 GPU 한 장의 메모리 사용량은 줄지 않는다. 모든 GPU가 똑같은 것을 들고 있기 때문이다.

학습 중 GPU 메모리에 있는 것

  • 모델 파라미터
  • 기울기
  • 옵티마이저 상태 ← 가장 큼. AdamW는 파라미터마다 모멘트 2개를 FP32로 저장 → 파라미터 개면 바이트

ZeRO [Rajbhandari et al., 2019]는 이 중복을 없애 각 GPU가 일부만 맡게 하고, 필요할 때만 통신으로 모은다.

그림의 기호: = 파라미터 수, = 옵티마이저 상태의 파라미터당 바이트 수, = GPU 수. 혼합 정밀도 Adam을 가정해 파라미터·기울기는 FP16(각 바이트), 옵티마이저 상태는 (FP32 마스터 파라미터 4 + 1차 모멘트 4 + 2차 모멘트 4바이트)이다.

💡 위의 과 는 왜 다른가 — 위에서 센 은 모멘트 2개(FP32, 4+4바이트)뿐이다. ZeRO 논문은 혼합 정밀도 학습을 가정한다. 순전파·역전파는 FP16 사본(파라미터 2바이트)으로 하지만, FP16으로 작은 갱신을 계속 더하면 반올림에 묻혀 사라지므로 옵티마이저가 갱신할 FP32 원본(마스터 파라미터) 4바이트를 따로 둔다. 이것도 옵티마이저만 쓰는 값이라 옵티마이저 상태로 셈하고, 가 된다. WebBot( = 152,316,672)이면 모멘트만 ≈ 1.22GB, 마스터 파라미터까지 ≈ 1.83GB다. 저장소의 ch09/01_pretrain.py는 파라미터를 FP32로 두고 BF16 autocast만 쓰므로 따로 둔 마스터 사본이 없어, 옵티마이저 상태가 다.

Baseline (일반 데이터 병렬) 없음 120GB

ZeRO-2 () + 기울기 16.6GB

ZeRO-1만으로도 메모리가 1/4로 준다. 옵티마이저 상태가 그만큼 큰 비중을 차지한다는 뜻이다.

ZeRO-1은 스텝마다 무엇을 하나

옵티마이저 상태를 나눠 가지면, 각 GPU는 자기 조각에 해당하는 파라미터만 갱신할 수 있다. 그래서 한 스텝이 다음처럼 바뀐다(GPU 4장, 파라미터를 4조각으로 나눈 경우).

  1. 순전파·역전파는 일반 데이터 병렬과 같다. 모든 GPU가 파라미터 전체를 들고, 자기 배치로 기울기 전체를 계산한다.
  2. 기울기를 GPU끼리 평균한다. GPU 는 자기 조각 의 평균 기울기만 있으면 된다.
  3. GPU 는 자기가 들고 있는 조각 의 모멘트(와 마스터 파라미터)로 파라미터의 1/4만 갱신한다.
  4. 갱신된 조각 4개를 모든 GPU에 다시 모은다(all-gather). 이제 모든 GPU의 파라미터가 다시 같아진다.

옵티마이저 상태는 GPU마다 1/4만 있으면 되므로 가 된다. 대가는 4단계의 파라미터 모으기 통신이다. ZeRO-2는 2단계에서 자기 조각의 기울기만 남기고 나머지를 버려 기울기도 나누고, ZeRO-3는 1단계에서도 파라미터를 층마다 모았다 버린다.

사용처: 마이크로소프트 DeepSpeed 라이브러리, 파이토치의 torch.distributed.fsdp(FSDP, 비슷한 기능).

9.5 Muon 옵티마이저

Muon (Momentum Orthogonalization by Newton-Schulz) [Jordan et al., 2024] — 메모리를 적게 쓰면서 빨리 수렴해 주목받는 옵티마이저.

AdamW Muon
다루는 단위 원소 하나하나 독립 가중치 행렬 전체
저장하는 상태 1차 + 2차 모멘트 (FP32 2개) 1차 모멘트만
갱신 방향 (원소별 스케일) 1차 모멘트 행렬을 직교화한 것
적용 대상 모든 파라미터 2차원 행렬만 (편향·RMSNorm 가중치 불가)
  • 직교화: 기울기(모멘텀) 행렬의 각 방향이 비슷한 크기를 갖도록 맞추는 연산. 특정 방향으로 갱신이 지나치게 커지는 것을 막는다.
  • 2차 모멘트를 저장하지 않으므로 옵티마이저 상태 메모리가 AdamW의 절반이다.

💡 보충 (책 범위 밖) — 모멘텀 행렬을 특잇값 분해 했을 때 를 모두 1로 바꾼 가 "직교화된" 행렬이다. SVD는 비싸므로 행렬곱만으로 이를 근사하는 반복 계산이 이름에 들어간 Newton-Schulz 반복이다.

파이토치 2.9부터 torch.optim.Muon으로 쓸 수 있다. 행렬에만 적용되므로 Muon + AdamW 하이브리드로 구성한다.

from torch.optim import Muon, AdamW

muon_params  = [p for p in model.parameters() if p.ndim == 2]   # 2차원 텐서(행렬)
adamw_params = [p for p in model.parameters() if p.ndim != 2]   # 그 밖 (편향, RMSNorm 등)

optim1 = Muon(muon_params, lr=0.02)        # 학습률도 서로 다르게
optim2 = AdamW(adamw_params, lr=3e-4)

loss.backward()
optim1.step(); optim2.step()
optim1.zero_grad(); optim2.zero_grad()

⚠️ 저장소의 ch09/01_pretrain.py는 Muon이 아니라 torch.optim.AdamW만 쓴다. 위 코드는 책에 실린 예시다.

9.6 Weights & Biases (W&B)

학습 중 손실·학습률 변화를 실시간으로 기록·시각화하는 도구. wandb 패키지를 설치하고 몇 줄만 추가하면 된다.

import wandb
wandb.init(project='webbot')                                # 프로젝트 초기화
for step, (inputs, targets) in enumerate(dataloader):
    loss = train_step(model, inputs, targets)
    wandb.log({'loss': loss.item(), 'step': step})          # 지표 기록 → 웹 대시보드
wandb.finish()

여러 실험을 겹쳐 비교하거나, 하이퍼파라미터와 성능의 관계를 분석할 때 유용하다.

    device = torch.device(f'cuda:{local_rank}')
    torch.cuda.set_device(device)
    seed_offset = int(os.environ['RANK'])            # 랭크마다 시드를 달리 → 서로 다른 배치
else:
    device, local_rank, seed_offset = get_device(), 0, 0
is_main = (not ddp) or (local_rank == 0)             # 로그·평가·저장은 랭크 0만
torch.manual_seed(42 + seed_offset)

model = torch.compile(model)                         # 그래프 컴파일로 고속화
if ddp:
    model = DDP(model, device_ids=[local_rank])

for step in pbar:
    lr = get_lr(step, learning_rate, warmup_iters, max_iters)   # 6장의 D2Z 그대로
    for g in optimizer.param_groups:
        g['lr'] = lr
    optimizer.zero_grad()

    for micro_step in range(accumulation_steps):                # ── 기울기 누적
        batch_x, batch_y = get_batch(train_data, context_len, micro_batch_size, device)
        with autocast(device_type='cuda', dtype=torch.bfloat16):
            logits = model(batch_x)
            loss = F.cross_entropy(logits.view(-1, logits.size(-1)), batch_y.view(-1))
            loss = loss / accumulation_steps
        if ddp and micro_step < accumulation_steps - 1:
            with model.no_sync():                               # ⭐ 중간 단계는 All-Reduce 생략
                loss.backward()
        else:
            loss.backward()                                     # 마지막에만 동기화

    torch.nn.utils.clip_grad_norm_(model.parameters(), grad_clip)
    optimizer.step()
    if is_main:
        wandb.log({'train/loss': loss.item() * accumulation_steps, 'train/lr': lr}, step=step)

💡 model.no_sync() — DDP는 backward()마다 All-Reduce를 한다. 기울기 누적 중에는 어차피 마지막에 한 번만 합치면 되므로, 중간 마이크로배치에서는 동기화를 꺼서 통신 비용을 로 줄인다.

💡 평가할 때는 model.module(DDP가 감싼 원래 모델)을 꺼내 랭크 0에서만 evaluate()를 돌린다. 평가 함수와 get_batch()는 6장과 같다.

⚠️ 유효 배치 128은 GPU 1장 기준이다. DDP로 GPU 장을 쓰면 전역 배치는 가 된다. 또 evaluate()와 학습 루프의 autocast가 device_type='cuda'로 고정되어 있어 이 스크립트는 사실상 CUDA GPU 전용이다.

한눈에 보기: WebBot 학습 한 스텝과 GPU 메모리

이 장의 기법이 ch09/01_pretrain.py의 옵티마이저 스텝 하나 안에서 어디에 들어가는지 (a)에 그렸다. 실제 설정(마이크로배치 32, 컨텍스트 1,024, 누적 4)을 그대로 쓰고, GPU는 2장으로 가정했다. (b)는 webbot/model.py로 만든 실제 WebBot의 파라미터 수 로 GPU 한 장이 들고 있어야 하는 메모리를 계산한 것이다.

  • 한 스텝 = 마이크로배치 4개. 마이크로배치 하나는 토큰이고, GPU 한 장의 스텝 하나는 그 4배인 131,072토큰이다. 10만 스텝이면 GPU 1장 기준 약 131억 토큰을 본다.
  • 기울기 누적은 .grad에 더하기만 한다. 손실을 4로 나눴으므로 쌓인 기울기는 유효 배치 128의 평균 손실의 기울기와 같다(9.1절). 활성값은 마이크로배치 32개분만 메모리에 있으면 된다.
  • 통신은 스텝마다 한 번. 마이크로 1~3은 no_sync() 안에서 역전파해 통신을 건너뛰고, 마이크로 4의 backward()가 All-Reduce를 함께 한다. 그래서 두 GPU는 같은 기울기로 갱신하고, 가중치가 늘 같다.
  • 랭크마다 다른 데이터. 시드가 42 + RANK라 get_batch가 랭크마다 다른 위치를 뽑는다. 같은 배치를 뽑으면 GPU를 늘린 의미가 없다.
  • 옵티마이저 상태가 가장 크다. 저장소 설정(FP32 AdamW)에서 2.44GB 중 1.22GB가 1·2차 모멘트다. Muon 하이브리드는 2차 모멘트가 없어 1.83GB가 되고, ZeRO-1은 상태를 4장에 나눠 2.44GB를 1.07GB로 줄인다. WebBot의 1차원 파라미터(RMSNorm 가중치)는 19,200개뿐이라 Muon이 거의 전부를 맡는다.
  • 활성값은 이 막대 밖에 있다. 기울기 누적과 체크포인트가 줄이는 것은 활성값이고, ZeRO와 Muon이 줄이는 것은 막대 안의 세 항목이다. 두 묶음은 서로 다른 메모리를 아끼므로 함께 쓸 수 있다.

핵심 정리

  • 기울기 누적: 마이크로배치의 손실을 accumulation_steps로 나눠 backward()를 반복하고, 번마다 한 번 step(). 메모리는 작은 배치만큼, 효과는 큰 배치만큼.
  • 기울기 체크포인트: checkpoint(block, x, use_reentrant=False) — 블록 입력만 저장하고 중간 출력은 역전파 때 블록 순전파를 한 번 더 돌려 재계산. 메모리와 시간(약 순전파 한 번)을 맞바꾼다.
  • 데이터 병렬(DDP): 같은 모델을 GPU마다 복제하고 데이터를 나눠 처리, All-Reduce로 기울기를 합쳐(DDP는 GPU 수로 나눈 평균) 모두 같은 갱신을 한다. torchrun --nproc_per_node=N으로 실행. 기울기 누적과 함께 쓸 때는 no_sync()로 중간 통신을 생략한다.
  • ZeRO: 데이터 병렬의 중복 저장을 없앤다. 옵티마이저 상태(ZeRO-1) → 기울기(ZeRO-2) → 파라미터(ZeRO-3) 순으로 분할, 7.5B·64 GPU 예에서 120GB → 1.9GB.
  • Muon: 2차원 가중치 행렬의 모멘텀을 직교화해 갱신하고 2차 모멘트를 저장하지 않는다. 1차원 파라미터는 AdamW가 맡는 하이브리드 구성.
  • W&B로 학습 곡선을 실시간 관찰. WebBot(150M)은 10만 스텝 후 검증 손실 약 3.0 — 문법과 패턴은 익혔지만 사실 정확도와 설명 능력은 부족하다 → SFT·DPO·GRPO의 몫.

복습 질문

  1. 기울기 누적에서 손실을 accumulation_steps로 나누지 않으면 어떻게 되는가? 학습률과는 어떤 관계가 있을까?

    정답 보기

    손실을 나누지 않으면 .grad에는 마이크로배치 평균 손실의 기울기가 4개 더해진다. 큰 배치 한 번의 기울기(평균)보다 accumulation_steps배(배) 큰 값이다(9.1절의 식에서 이 빠진 것).

    SGD라면 갱신량이 이 되므로 학습률을 배 키운 것과 같다. 학습이 불안정해지거나 발산할 수 있다. AdamW는 로 크기를 정규화하므로 영향이 훨씬 작지만, ch09/01_pretrain.py처럼 clip_grad_norm_(…, 1.0)을 쓰면 노름이 배가 되어 클리핑이 훨씬 자주 걸린다. 결국 "큰 배치 한 번과 같은 학습"이 아니게 된다.

  2. 기울기 누적과 기울기 체크포인트는 둘 다 메모리를 아끼지만 방식이 다르다. 각각 무엇을 희생하는가?

    정답 보기
    • 기울기 누적은 배치를 쪼개 한 번에 메모리에 올리는 활성값을 줄인다. 대신 마이크로배치를 차례로 처리하므로 스텝 하나에 걸리는 시간이 늘어난다(큰 배치를 한 번에 병렬로 돌리지 못한다). 갱신 횟수당 계산량 자체는 같다.
    • 기울기 체크포인트는 배치는 그대로 두고 블록 안의 중간 출력을 저장하지 않는다. 역전파 때 그 블록의 순전파를 다시 계산하므로 계산량(시간)이 늘어난다.

    둘 다 활성값만 줄인다. 파라미터·기울기·옵티마이저 상태는 그대로이므로, 이쪽은 ZeRO나 Muon의 몫이다(한눈에 보기 그림 (b)).

  3. 데이터 병렬에서 All-Reduce를 하지 않고 각 GPU가 자기 기울기로만 갱신하면 어떤 문제가 생기는가?

    정답 보기

    GPU마다 다른 데이터를 받으므로 기울기도 다르다. 각자 자기 기울기로 갱신하면 첫 스텝부터 모델 사본의 가중치가 서로 달라진다. 그러면 하나의 모델을 큰 배치로 학습하는 것이 아니라, 데이터의 1/4씩만 본 서로 다른 모델 4개를 따로 학습하는 셈이 된다.

    GPU를 늘려도 유효 배치가 커지지 않고, 각 모델이 본 데이터만 줄어든다. ch09/01_pretrain.py는 랭크 0의 모델만 평가·저장하므로, 결과물은 나머지 GPU의 학습을 전혀 반영하지 못한다.

  4. DDP와 기울기 누적을 함께 쓸 때 no_sync()가 필요한 이유는?

    정답 보기

    DDP는 backward()를 부를 때마다 All-Reduce를 한다. 기울기 누적 중에는 마이크로배치 4개의 기울기를 다 더한 뒤 마지막에 한 번만 합치면 충분하다. All-Reduce(합·평균)는 선형이라 "4번 각각 합치고 더하기"와 "다 더한 뒤 한 번 합치기"의 결과가 같기 때문이다.

    그래서 no_sync() 없이도 결과는 같지만, 통신을 번(여기서는 4번) 하게 된다. no_sync()로 중간 마이크로배치의 동기화를 끄면 통신 비용이 로 준다.

  5. 데이터 병렬만으로는 "GPU 한 장에 안 들어가는 모델"을 학습할 수 없는 이유는? ZeRO-3는 이를 어떻게 해결하는가?

    정답 보기

    데이터 병렬은 모든 GPU가 모델 전체를 복제해 들고 있는 방식이다. GPU 한 장이 파라미터·기울기·옵티마이저 상태 전체()와 활성값을 감당해야 하므로, 이것이 한 장에 들어가지 않으면 GPU를 몇 장 늘려도 시작조차 할 수 없다. GPU를 늘려도 GPU당 메모리는 줄지 않는다.

    ZeRO-3는 옵티마이저 상태·기울기에 더해 파라미터까지 GPU 수로 나눠 각 GPU가 씩만 저장한다. 어떤 층을 계산할 때만 그 층의 파라미터를 통신으로 모아 쓰고 다시 버린다. 그래서 GPU당 메모리가 가 되어, 7.5B·GPU 64장 예에서 120GB가 1.9GB로 준다. 대가는 늘어난 통신량이다.

  6. ZeRO-1만 적용해도 메모리가 크게 줄어드는 이유를 식으로 설명하라.

    정답 보기

    GPU당 메모리 에서 이므로, 전체 중 옵티마이저 상태가 로 3/4를 차지한다. 파라미터와 기울기는 합쳐서 뿐이다.

    ZeRO-1은 이 가장 큰 항만 로 나눠 가 된다. 가 크면 둘째 항이 거의 사라져 , 즉 원래의 약 1/4에 가까워진다. 7.5B·GPU 64장이면 120GB → 31.4GB이고, WebBot(M)을 GPU 4장으로 나누면 2.44GB → 1.07GB다(한눈에 보기 그림 (b), ch09/flow_graph.py로 계산).

  7. Muon을 모든 파라미터에 적용할 수 없는 이유는? AdamW보다 메모리를 덜 쓰는 이유는?

    정답 보기

    Muon은 모멘텀 행렬을 직교화해 행렬의 여러 방향이 비슷한 크기로 갱신되게 한다. 이 연산은 2차원 행렬에만 정의되므로, 편향이나 RMSNorm 가중치 같은 1차원 벡터에는 적용할 수 없다. 그래서 p.ndim == 2인 파라미터만 Muon에, 나머지는 AdamW에 맡기는 하이브리드로 구성한다.

    메모리를 덜 쓰는 이유는 2차 모멘트를 저장하지 않기 때문이다. AdamW는 파라미터마다 1·2차 모멘트 2개(FP32면 8바이트)를 두지만 Muon은 1차 모멘트 하나(4바이트)만 둔다. WebBot은 파라미터 152,316,672개 중 2차원 행렬이 152,297,472개라 거의 전부가 Muon 쪽이고, 옵티마이저 상태는 약 1.22GB → 0.61GB로 절반이 된다(ch09/flow_graph.py로 계산).

  8. WebBot이 "Python was created by"에 틀린 답을 하고, "Machine learning is defined as"에서 같은 말을 반복하는 이유는 무엇일까? 어떤 학습 단계로 개선할 수 있을까?

    정답 보기

    사전 학습은 웹 텍스트에서 다음 토큰 예측만 학습한다. 모델이 배운 것은 "그럴듯하게 이어지는 문장"이지 "사실인 문장"이 아니다. "Python was created by" 뒤에 "the team at UC Berkeley"는 문법적으로 자연스럽고 그럴듯한 패턴이다. 150M이라는 작은 모델이 검증 손실 약 3.0까지 학습한 상태로는 드물게 나오는 사실을 정확히 기억하기 어렵다. 반대로 요일처럼 데이터에 아주 자주 나오는 패턴은 정확히 이어 간다.

    반복도 같은 이유다. 모델은 정의를 "설명"하도록 학습된 적이 없고, temperature=0.5로 확률이 높은 토큰을 고르다 보면 앞에 나온 구절이 다시 가장 그럴듯한 이어짐이 되어 같은 말이 되풀이된다.

    개선은 노트의 "다음 단계" 그대로다. 사실 지식은 스케일링 법칙에 따라 모델과 데이터를 키워 늘리고(8장), 질문에 답하고 개념을 설명하는 형식은 SFT로, 더 정확하고 반복 없는 답을 고르는 것은 DPO·GRPO 같은 선호·보상 학습으로 가르친다(3장, 6장).
